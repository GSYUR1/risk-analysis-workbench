# 新客授信透视聚合底表

## 输出与字段

本功能生成 `SELECT 维度, 聚合指标 FROM 新客授信宽表 [LEFT JOIN 维表] GROUP BY 维度` 的SQL；一行是一个维度组合，用作后续Excel透视或分子分母汇总的底表，不是最终风险比率展示，也不是明细宽表重建。

字段的唯一有序清单为 `pivot_base_profile.json`，依据2026-10-21用户提供的表头登记：默认9个维度 + 140个指标，共149列。`cre_cnt`及其后都是指标。按本次任务替换、增加或减少维度，但默认保留全部140个指标；不添加未要求的风险观察点、复借指标或比率。保留 `deal_amobilewalla_multi_norecord_cnt` 的原拼写，不自行纠正。

维度未指定时采用清单中的9个维度；用户指定维度时只按指定维度分组，不附加用户ID、订单ID或全部维度两两交叉。`dimensions: []` 表示全样本汇总。未匹配维度保留NULL或使用已确认缺失标签，不自动归入“未命中”。

## 区分两种来源

1. **已加工指标列的宽表（indicator）**：来源表口径中的 `ph_risk.cx_ph_newcust_cre_indicator`。在申请粒度、指标完整、定义一致的前提下，对140列分别 `SUM(b.字段) AS 字段`；`cre_cnt`也是求和，不能以 `COUNT(*)` 计算分组行数。不得平均风险率、通过率或均值。
2. **原始明细宽表（detail）**：来源表口径中的 `ph_risk.cx_ph_newcust_cre_order_trace`。需要将全部140个指标映射为经核实的聚合表达式，例如 `COUNT(DISTINCT b.credit_apply_no)`、`SUM(CASE WHEN b.is_approve=1 AND b.is_credit=1 THEN b.credit_amount_after END)`、`SUM(b.dpd1_7)`。不能对不存在的 `cre_cnt`、`deal_*` 等目标列盲目SUM。

先按现有工具优先级核对口径：`ph_data_analysis`没有SQL生成函数，因此生成器负责拼装，业务表达式来自现行 `metric_registry.yaml`、宽表原SQL和本次确认。部分registry表达式是对indicator列的二次求和，不是order_trace的原始表达式；不得整份直接套用。detail模式必须提供完整 `metric_expressions` 和 `metric_expression_evidence`，缺失即停止生成，不删列、不猜公式。

本地历史核对（不是实时结构确认）：征信项目的2026-10-20 indicator结构快照缺少 `cre_rating_version_merge`、`cibi_trade_active_cnt_bin`、`cibi_trade_cnt_bin`、`deal_cibi_trade_cnt_sum`、`deal_cibi_trade_cnt_cnt`。该快照位于 `D:\工作文件\03_分析文档\01_菲律宾\260826_征信借贷类型分析\risk-analysis\analyses\20261020_A12借贷机构类型增量分层分析_b165fe1eb7c0\runs\20261020_141412_schema_indicator\stdout.json`。这意味着不能宣称默认SQL已可在线执行；正式使用时经授权用 `odps-query` 复核当前表。维度缺口可按下节补充；指标缺口需追溯原SQL/确认数据源，或完整映射detail模式，不能静默用0/NULL凑齐。已有本地原SQL未包含最后两个trade指标，不能仅凭字段名推断有效样本口径。

本功能是全授信链路底表需求，不自动套用默认“新客成交”的 `is_payout=1`；时间、渠道、机型、产品、评级、分区等条件按本次确认。只有用户明确要求成交范围时才加成交筛选。金额保留来源PHP单位，不自动除以61；保留源NULL语义，不在生成器中把无成熟样本补成零风险。

## 补充维度

- 优先用主宽表已有字段；缺少时才读取维度口径和来源表口径，确认表、键、分区、有效时点及字段来源。
- 默认 `LEFT JOIN` 保留主样本。按实际键关联，例如 `credit_apply_no`，不能因为有 `user_id` 就忽略一人多次授信。支持复合键。
- 维表关联键必须唯一。多条快照先按经确认的申请前时点/版本规则加工成唯一关系，禁止随意 `DISTINCT`、`MAX` 或无序 `ROW_NUMBER`。申请前快照/复杂时态关联先形成已确认的申请粒度关系，再交给生成器；不自动取最新记录造成未来信息泄漏。
- 维表分区/范围条件放维表子查询，不放最终WHERE造成隐式内关联。生成器仅支持基于主表字段的等值LEFT JOIN；不提供静默更改样本的INNER JOIN。
- `.checks.sql`包含主键缺失/重复、维表重复键、关联前后行数和未匹配数。先执行检查，缺失主键、重复键或扩行时停止正式聚合；匹配率按已确认方案验收。生成SQL不代表这些检查已经通过。

## 调用参数

`工具/pivot_base_sql.py --spec <JSON路径> --output <新SQL路径>`。以下仅示例，不是默认时间窗，维表名和字段也不代表已经核实可用：

```json
{
  "source_kind": "indicator",
  "filters": ["trace_date >= '2026-05-01'", "trace_date < '2026-11-01'"],
  "dimensions": ["trace_mth", "cre_rating_sub", {"name": "extra_bin", "expression": "extra.extra_bin"}],
  "joins": [{
    "alias": "extra",
    "table": "ph_risk_dev.confirmed_credit_dimension",
    "keys": {"credit_apply_no": "credit_apply_no"},
    "filters": ["pt = 'confirmed_partition'"]
  }]
}
```

- `source_kind`必须显式为`indicator`或`detail`；不从列名猜测。`source_table`可指定已核实的同口径表，否则从profile选择。
- `dimensions`省略时为清单9列；字符串表示`b.同名字段`，对象为`name` + `expression`。表达式可以引用`b`与已声明维表别名，先投影再分组。
- `filters`是主表SQL条件列表，不带别名；全量必须显式`allow_all_dates: true`，不复制历史SQL中的起始日。
- `grain_keys`默认`["credit_apply_no"]`，作为申请唯一性验收；如需更改必须有实际粒度依据。不能通过扩大键列表掩盖一笔授信重复。
- `source_columns`可放从当前describe结果取得的完整主表列名列表；生成器对直接引用字段检查缺失。复杂表达式、类型、维表字段、分区与时点仍需人工/查询校验，不能把`schema_supplied`当成全SQL已验证。
- detail模式的`metric_expressions`键必须精确覆盖140列，值使用主表别名`b`的完整聚合表达式；`metric_expression_evidence`记录来源文件、哈希、口径key及本次确认。生成器不会验证业务公式真伪。
- SQL片段是受信任的分析配置，不是通用SQL安全沙箱；生成后按审批规范审阅。生成器没有数据库连接或DDL/DML执行能力。

## 验收和下游

1. 先核对全量字段存在、类型可聚合、主表粒度及成熟度；schema缺字段时明确报告，不能丢掉指标后声称完成。
2. 保存spec、生成SQL、checks和manifest到当前事项目录`sql/`；manifest记录字段顺序、profile/spec哈希、`not_executed`状态，不覆盖旧文件。
3. 经授权通过 `odps-query` 执行检查；通过后才执行聚合。仅“加功能/生成SQL”不授权远程运行或建表；落表按既有审批与生命周期规则。
4. 输出顺序必须为指定维度 + 完整140指标；维度组合唯一。检查NULL分组未被丢弃；对全部指标做全量及按月汇总守恒核验，DOUBLE尾差与实质差异分别标记。若涉及distinct计数，先确认一个申请不会落入多个维度组，不能仅凭各组求和假定可加。
5. 比率在后续按 `SUM(分子)/SUM(分母)` 计算；成熟分母为0显示NA/空白。不要将这些已分组数据直接传给当前 `ph_data_analysis.generate_indicator/generate_pivot`：它们假定申请/订单明细粒度，会把汇总flag当成一笔。若要使用现成展示函数，回到其支持的明细粒度；否则仅基于本底表的分子/分母做加权汇总并使用标准导出层。
